# Writing and Communication Rules

The project owner (Rahul) writes conversationally and directly. The product should sound like him. These rules apply to UI copy, error messages, documentation, marketing content, commit messages, code comments, and PR descriptions.

The default register is **professional but human**. We are not Apple's marketing department. We are not a robot. We are a person who knows what they are talking about, writing for another person who wants to get something done.

## Hard avoids

These patterns are immediately flagged in any text generated by or reviewed by an agent. If you find yourself writing one of these, rewrite the sentence.

### AI tells

- "I'd be happy to help with that"
- "Certainly!" / "Absolutely!" / "Of course!"
- "Great question"
- "Let me know if you need anything else"
- "Here's a comprehensive overview of..."
- "Let's dive into..."
- "It's important to note that..."
- "Furthermore" / "Moreover" / "Additionally" used as paragraph openers
- "In today's fast-paced world..."
- "Whether you're a beginner or an expert..."

### Corporate jargon

- "Leverage" (use → "use")
- "Utilize" (use → "use")
- "Synergy", "synergize"
- "Best-in-class"
- "Cutting-edge"
- "Revolutionary" / "disruptive" / "game-changing"
- "Robust solution"
- "Seamless experience" / "seamlessly"
- "Empower" / "empowering"
- "Unlock the potential of..."
- "World-class"
- "Mission-critical"

### Filler

- "Basically"
- "Essentially"
- "At the end of the day"
- "It goes without saying"
- "Needless to say"
- "Without further ado"

### Passive voice in user-facing text

- "The file was processed" → "Sangeet finished processing the file."
- "Restoration is recommended" → "We recommend running restoration."
- "The model will be downloaded" → "Sangeet is downloading the model."

Passive voice is acceptable in technical documentation where the agent is genuinely unknown or unimportant, but rare even there.

## Voice and tone

### Be direct

- Lead with what the user needs to know. The most important sentence is the first one.
- Cut throat-clearing. If a paragraph starts with "It's worth mentioning that..." delete that phrase and start with the actual point.
- Short sentences. Average around 15 words. Long sentences are fine occasionally for rhythm; never two in a row.

### Be specific

- "Faster" is weak. "About 2x realtime on M2" is strong.
- "Better quality" is weak. "Removes broadband hiss without smearing tabla transients" is strong.
- Numbers and specifics build trust. Vague superlatives erode it.

### Be human

- Use "you" and "your" when addressing the user. Not "the user".
- Use "we" when talking about the team or the product. Not "Sangeet AI Inc." or "the application".
- Contractions are fine — "you're", "we'll", "doesn't". They sound human.
- Humor is fine in moderation. Sarcasm is not.

### Be honest

- Do not promise what we cannot deliver. If a result is not guaranteed, say so.
- Do not call beta features "production-ready". Do not call slow operations "fast".
- When something goes wrong, say so directly. Do not minimize ("a minor issue") and do not catastrophize ("a critical failure occurred").

## Specific contexts

### Error messages

Structure: **what happened, what it means, what to do.**

Bad:
> Error 0x80004005: Operation failed unexpectedly.

Good:
> Sangeet couldn't read this file. It looks like the file may be corrupted or in a format we don't support yet. You can try converting it to WAV or FLAC and importing again.

Rules:
- No error codes shown to the user (log them with `request_id` for support).
- Never blame the user. "You gave me a bad file" → "This file looks corrupted."
- Always offer a next step. If there is no next step, say "We're looking into this — sorry for the trouble" and log the issue.

### Button labels

- Verbs, not nouns. "Restore" not "Restoration". "Export" not "Export Options".
- Short. Two words is plenty. One is often better.
- Title case for primary actions ("Restore Audio"), sentence case for secondary actions ("Show advanced options").
- No exclamation marks. Never. Not even on success buttons.

### Empty states

- Don't be cute. "Nothing here yet, you sad lonely person" — no.
- Explain what would normally be here and how to get something there. "Drop an audio file to start your first restoration."

### Progress indicators

- If you know the percentage, show it. "Restoring — 47%"
- If you know the stage, show it. "Restoring — analyzing audio"
- If you know neither, do not lie with a fake progress bar. Show "Restoring..." with a spinner.

### Notifications

- One sentence each. Two at most.
- No notification for things the user can already see. If the export window shows the file, do not also send a desktop notification.

## Documentation

### README

- Top-of-readme is "what this is, in one sentence". Then a 2-3 sentence elevator pitch. Then install. Then quick start.
- No marketing fluff at the top. No "Built with ❤️ in Pune." No badges that have nothing to do with the project's quality.
- Screenshots are welcome but optional. If you include them, they must be current. Stale screenshots are worse than no screenshots.

### Code comments

See `01-coding-standards.md`. Comments explain *why*, not *what*. Audio engineering rationale is comment-worthy and always welcome.

### ADRs (Architecture Decision Records)

Format:

```markdown
# ADR-NNN: Short title in imperative form

Date: YYYY-MM-DD
Status: Proposed | Accepted | Superseded by ADR-NNN

## Context
What problem are we solving? What are the constraints?

## Decision
What did we decide?

## Consequences
What gets better? What gets worse? What are we now committed to?

## Alternatives considered
What else did we look at? Why did we reject them?
```

One page. No more. If an ADR needs more than one page, the decision is too big and needs to be split.

### Commit messages

See `01-coding-standards.md`. Conventional Commits format.

Subject is a sentence in imperative mood: "fix(router): handle 8 kHz input sample rate" not "Fixed router 8kHz issue."

Body explains *why* this commit exists. Do not paraphrase the diff in prose — the diff is right there.

### PR descriptions

Four sections, in order:

1. **What changed** — one sentence
2. **Why it changed** — the user-visible or engineering-visible problem this solves
3. **How to verify** — concrete steps a reviewer or future bisector can run
4. **Risks** — what could go wrong, what to watch for

For restoration-chain PRs, additionally include the eval harness delta. See `06-testing-and-eval.md`.

## Marketing content (LinkedIn posts, articles, landing page)

The same rules apply. Specifically:

- Lead with a concrete observation, not an abstraction.
- Show, do not tell. "Here's what a 1965 Rafi recording sounds like before and after" beats "transformative AI-powered restoration".
- Numbers, not adjectives.
- Personal voice. Rahul writes in first person. The brand can too where it makes sense.
- No emojis in headlines. Sparingly in body. Never as bullet points.

## When asked to "make it sound more professional"

Resist. "Professional" often means "more corporate jargon and passive voice", which violates these rules. Push back and offer a clearer version that retains directness.

## When asked to "make it longer"

Also resist. Length without substance is filler. If the content genuinely needs more depth, add more substance, not more words.
